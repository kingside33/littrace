# [U6] 引导文案按服务状态分支:菜单项与卡片标题同源切换(offline / incompatible)

- 日期:2026-11-18
- 状态:已接受

## 背景

S4 的探测把「服务在运行但版本/协议不兼容」判为 `unsupported`,映射成
`SERVICE_STATES.INCOMPATIBLE`(`plugin/src/menus/menuCore.mjs:86-101`)。这一
状态的字面事实是:**服务回答了**,只是版本不对。

原先前端的引导文案不区分这一点:引导菜单项一律写「本地服务未运行」,引导卡片
标题也写「本地服务未运行」。而卡片正文在 incompat 分支已经改口成「可以连接,
但版本与本插件不兼容」。于是同一张卡片上,标题说「没运行」、正文说「能连上
但不兼容」,自相矛盾;菜单项同样在撒谎。

这个矛盾不是措辞问题:它把用户指向了错误的下一个动作。「启动」与「更新」是
两件不同的事,而标题只给了前者。

## 决策

把状态到文案键的选择**上移到契约表与纯函数**,而不是在绘制层拼字符串:

- 契约表给引导条目加 `incompatibleLabelKey`(`menuCore.mjs:217,273`,两个
  入口:条目右键子菜单与 Tools 菜单);
- `GUIDE_CARD` 加 `incompatibleTitleKey`(`menuCore.mjs:738`);
- `labelKeyOf(entry, service)`(`menuCore.mjs:677`)只在状态为 `incompatible`
  且条目声明了该键时返回它,其余条目保持静态键;
- `guideView()`(`menuCore.mjs:767`)按状态选标题键与正文首行;
- `menus.ts` 绘制时把 `data-l10n-id` 一并更新(`menus.ts:188-218` 的
  `paintElement()`,状态选键在 `:225-239`),否则窗口的 Fluent 覆盖层稍后会按
  旧 id 把标签替换回另一变体。

两条键各进 zh-CN / en-US 两份 FTL,测试断言两份 bundle 都存在;键选择是纯函数,
进 node 测试并登记 ci.yml。

## 备选

- **备选 A:只改正文,标题维持「未运行」**。否决:矛盾仍在,只是从「标题 vs
  正文」变成「标题 vs 事实」;用户读到的第一行仍然是假的。
- **备选 B:在 `t()` 里做字符串拼接(如 `t(base) + " / " + t(suffix)`)**。否决:
  文案会脱离 FTL——译者看不到完整句子,语序与标点在两种语言里也不同,而且
  Fluent 的属性/选择器机制完全用不上。
- **备选 C:把两个状态合并成一条含糊文案(如「本地服务不可用」)**。否决:会
  失去「启动」与「更新」这两个不同的下一步;U6 的验收就是「离线时入口明确
  禁用并给引导,绝不静默失败」,含糊文案等于把引导降级成一句废话。

## 后果

两份 `.ftl` 各多两条键,`menuCore.mjs` 多一条纯函数分支与其对应测试。菜单项与
卡片标题不再互相矛盾,两个状态的下一步动作各自明确(启动 / 更新后重新检查)。

维护约束:今后新增按状态变化的文案,应沿用「契约表加键 + 纯函数选键 + 绘制时
同步 `data-l10n-id`」这条路径,不要在边缘里拼字符串。
