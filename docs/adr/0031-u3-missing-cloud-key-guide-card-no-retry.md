# [U3] 云 key 缺失不提交任务、不提供重试,只给引导卡片

- 日期:2026-11-18
- 状态:已接受

## 背景

仓库纪律要求:免费功能的可用性依赖本地伴随服务,**服务离线或配置缺失时入口
明确禁用并给引导,绝不静默失败,也绝不半功能状态**(AGENTS.md「措辞纪律」)。

服务端侧,`qa.answer` 在 `cloud_enabled` 为 false 时直接抛错
(`kbapp/research/qa.py:58-59`),即提交一个这样的 run 必然失败。

## 决策

提问**提交前先读** `GET /api/status` 的 `cloud_enabled`
(`kbapp/workflows/status.py:57`);为 false 时**不创建 run**,直接追加一张
`GUIDE` 卡片:缺什么、去哪配、一个「去设置」动作(`plugin/src/readerPanelCore.mjs:1434`)。

`GUIDE` 与 `FAILURE` 是两种卡片:`GUIDE` 的 `retry` 恒为 `null`
(`plugin/src/readerPanelCore.mjs:674`),因为没有可重试的对象——重试只是把一次
注定失败的提交再做一次。服务端给出的配置类中文文案做**兜底分类**;字段缺失
(旧版服务不返回该字段)不当成「未配置」。

## 备选

- **备选 A:照常提交 run,失败后再按 `FAILURE` 卡片处理**。否决:会给用户一个
  对配置问题**完全无效**的重试按钮,并且在服务端创建一条注定失败的任务——用户
  连点几次就在任务列表里留下几条失败记录,却仍然没有 key。
- **备选 B:把「未配置」并入 `FAILURE` 卡片**。否决:外形相同但多一个误导性
  重试入口;并且「未配置」的语义就此丢失,无法被测试区分。

## 后果

未配置状态的语义由**卡片种类**承载(`guide` vs `failure`),测试可直接断言
`retry === null` 而不必看文案(`tests/test_plugin_reader.cjs`)。

代价是每次提问多一次 `/api/status` 请求;且需要一个认识服务端一句中文文案的
兜底分类——这是可接受的软耦合:字段缺失走默认、不猜测。
